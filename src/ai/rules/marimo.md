# Marimo Notebooks

- marimo requires every variable name to be globally unique across all cells in a notebook. Reusing a common name (e.g. `haircut`, `face_value`, `df`) in two different cells raises `MultipleDefinitionError` at runtime, not at write time, so it isn't caught by a type checker or linter.
- Default every cell-local variable to a leading underscore (e.g. `_face_value`, `_haircut`); underscore-prefixed names are private to the cell and exempt from the uniqueness rule. Only leave a variable unprefixed if another cell depends on it via `return foo,`.
- All imports go in the `with app.setup:` block. No per-cell imports.
- Give each UI selector its own standalone cell, separate from the logic that consumes it.
- Default to normal, directly readable Python: one setup cell with imports, editable inputs, and query setup, then one cell that reads and displays the data. Add more cells only when the task needs them. Omit text/Markdown cells by default; add them when an explanatory investigation is requested. Add UI inputs only when the user asks for interactive controls.
- Write Python directly in cells. Do not hide notebook logic in Python source strings passed to subprocesses, `exec`, or `eval` to work around missing dependencies. SQL query strings are fine.
- Set up a uv environment with Marimo and the notebook's dependencies so imports and execution work directly. Prefer the owning project's environment and verify the notebook runs in it. If that environment cannot support the notebook, ask Oscar whether to place it in a different repository/worktree or use a different environment instead of adding a subprocess workaround.
- Shared notebook utilities should expose small public functions for each useful boundary or transformation, such as fetch, validate, parse, and transform. A convenience function may compose those primitives for the common end-to-end path, but notebooks must also be able to call each stage directly.
- Keep one-off plumbing in the notebook until a second caller exists. Move it to `notebooks/utils/` when it isolates a non-trivial external boundary or is genuinely shared; do not create result models or wrappers that merely repackage one call.
- When Oscar asks to inspect a notebook, open it with `uv run marimo edit`, not `marimo run` or a static export, so the code remains visible alongside the results. Run it from the owning project (`~/anvil` for notebooks kept there) with `--host 0.0.0.0 --headless --watch`, keep the server running for review, and report the reachable URL and authentication token. When executing a notebook for results, use `marimo run --include-code` so the served notebook retains its code view too.
- If a synchronous client starts its own asyncio event loop (for example, `PIPSource.build_snapshot`), call it from an async Marimo cell with `await asyncio.to_thread(...)`. Calling it directly inside Marimo's running loop raises `RuntimeError: Cannot run the event loop while another loop is running`.
